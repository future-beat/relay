<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public dashboard → visitor | The dashboard is unauthenticated and now intentionally renders a credential |
| Repository → public | The demo key is committed to a public README by design (D-02) |
| Operator → live machine | Fly secrets are the only place the owner key exists |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-28 | Elevation of Privilege | Publishing a working credential on a public page | accept | Deliberate per D-02/SEC-06. The demo key is confined to the demo tier (5 runs/hour per IP) and bounded absolutely by the $5/day ceiling; it grants no owner-only surface. Openness is the portfolio statement and obscurity would add nothing |
| T-01-29 | Tampering | Dashboard advertising a key the service does not accept | mitigate | Rendered from `settings.demo_key` at serve time, never a hardcoded literal. A test monkeypatches the setting and asserts the rendered value follows |
| T-01-30 | Information Disclosure | Owner key accidentally rendered or committed | mitigate | Only `demo_key` is ever read by the dashboard handler; `.env` is gitignored; `.env.example` carries placeholders only |
| T-01-31 | Denial of Service | Dashboard 500 on an unconfigured deployment (`demo_key` unset) | mitigate | Falsy `demo_key` renders a neutral placeholder; the public landing surface must never fail |
| T-01-32 | Denial of Service | Deploying fail-closed auth before the Fly secrets exist, taking the live demo down | mitigate | Documented as a blocking ordered ops step in the README deploy notes, in `user_setup` frontmatter, and in the human checkpoint |
| T-01-33 | Repudiation | Eval regression from the new denial state transition going unnoticed | mitigate | The human checkpoint runs `relay.evals --limit 3` explicitly, because the unit suite structurally cannot observe eval pass rate |
</threat_model>
